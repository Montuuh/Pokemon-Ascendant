# Migration — from Project Ascendant (Unity) to Pokémon Ascendant (web)

> Source repo: `../ProjectAscendant` (read-only reference). Last Unity commit: `e895da2` (2026-07-15).
> What carried over: **design canon** (all of it, now in `docs/design`), **content values** (from the seeders),
> **tests as spec** (the EditMode suite guided the Vitest suite), **RNG core bit-compatibility**, **design
> tokens**, **art**. What did not: MonoBehaviours, ScriptableObject plumbing, event-channel assets, UI Toolkit,
> Addressables, the Coplay bridge and every dev tool built to work around it.

## 1. Why the port was low-risk

The Unity code was already ~68 % engine-free (146 of 216 logic files), `CombatController` was a POCO, content
was generated by C# seeders (code-as-data), and the determinism pillar means a recorded fight can be replayed
and diffed. The rules were the cheap part; the UI/art/feel that was never finished in Unity was built fresh where
it is cheap to iterate — the whole Combat Slice landed in one session on 2026-09-19.

## 3. Deliberate changes (not bugs)

- **15 types, not 18.** Canon says Gen I 15; the Unity enum carried neutral placeholders (OPEN G5 / Q25).
- **Reducers instead of a controller class + SO event channels.** Same rules, explicit state, free replay/dump.
- **Events array instead of event channels.** The UI animates from `state.events`.
- **JSON + Zod instead of ScriptableObjects.** Schemas keep the §10.3.2 field names where sensible.
- **No HSM class.** Game flow is data; the combat phase is a field on the state.
- **Notion retired.** `docs/design` is canon and git is its history; the Unity-era change log was folded into the prose it described.
- **UI Toolkit → React/CSS.** The HTML mockups became the components; the combat screen additionally shows the
  animated Showdown sprites over a stage backdrop, which the Unity build never had.

## 4. Numeric parity notes

- `GameRng` reproduces xorshift32 and the C# single-precision `Range01`/`PickWeighted` with `Math.fround`.
- **Stream seeding differs on purpose**: `RngStreams` applies `fmix32` to `runSeed ^ fnv1a(name)`. Unity used
  the raw XOR, whose first xorshift outputs are near-identical for nearby seeds (1001…1006 all rolled the same
  "randomness floor" outcome). A Unity replay is reproducible by seeding a `GameRng` with the raw XOR value.
- C# `float` config fields (`0.85f`, stage ladder) are doubles here; where an integer `floor` could flip, the
  golden-master fixtures are the arbiter.
- Effective stats: `base + growth × (level − 1)` reproduces the Unity flat growth curves exactly.

## 5. Golden-master procedure

`src/sim/replay/golden.test.ts` replays `src/sim/replay/fixtures/*.json` (seed + input log recorded by the
auto-player) and compares a fingerprint. A deliberate rules change regenerates them with `UPDATE_GOLDEN=1 npm test`
and a note in the section that changed; any other change that alters a fingerprint is a regression.

## 6. Reference: Unity-era combat-screen audit

`unity-combat-screen-audit.md` lists what was open when Unity stopped. Landed in v0.1: intent predicted damage,
combat log, phase markers, status/tier glyphs, hover/drag feel (click-select model), floating damage numbers,
attack/hit/faint motion, backdrop, consumable icons. Deferred: multi-enemy layout (v0.7), flee (Q26).
